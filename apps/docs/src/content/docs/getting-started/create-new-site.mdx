## Generate with the CLI

`@easy-web/cli` is a config-driven, create-only generator. It requires **Node.js 24 or later** and runs on the machine that creates the site. Nothing from it ships inside the site you generate, and it never deploys anything or touches a cloud resource.

Describe the site in a JSON file:

```json
{
  "target": "./new-site",
  "recipes": {
    "shell": { "siteName": "Example Site", "defaultLocale": "en", "noIndex": false },
    "auth": {}
  }
}
```

Then run the command:

```bash
easy-web create --config ./create.json
```

Install the package to get the `easy-web` command, or run it once with `pnpm dlx @easy-web/cli create --config ./create.json`.

What to expect:

- **Recipes.** The `shell` recipe is always selected. Leave out `auth` to skip sign-in. The `cms` recipe can extend a top-level content composition without taking ownership of its schemas or Astro configuration.
- **Offline by default.** Generation runs no package manager and makes no network request. It writes a placeholder `pnpm-lock.yaml` and makes one initial Git commit. Run `pnpm install` before you type-check or build, or pass `--install` to let the CLI run it through your own registry configuration.
- **A safe target.** The target must be a new or empty directory whose parent exists. Git needs an identity configured already; the CLI never changes your Git configuration.
- **Exit codes.** `0` is success, `3` is an invalid config, target or composition, and `4` is a generation, Git or staging failure. `--json` prints versioned diagnostics.

### Generate content pages without CMS

Add a top-level `composition` to create typed content collections and actual pages,
not just empty capability declarations:

```json
{
  "target": "./new-site",
  "recipes": {
    "shell": { "siteName": "Example Site", "defaultLocale": "en", "noIndex": true }
  },
  "composition": {
    "contentLocales": ["en"],
    "contentTypes": [{
      "id": "entries",
      "primary": true,
      "labels": { "en": "Entries" },
      "routes": { "en": "/entries/" },
      "traits": ["title", "slug", "summary", "image", "body"],
      "bindings": ["list", "detail", "navigation"]
    }]
  }
}
```

This generates a collection definition, example markdown, a typed adapter, a list
at `/entries/`, detail pages such as `/entries/example/`, and a navigation link.
The adapter proves the entry's capabilities and maps its summary/image into the
shared Card contract. The detail page renders markdown through Prose and uses
Media for the local Astro image asset. The capability graph includes the content
role and bindings; nothing is copied from a live website.

The first content slice accepts one locale matching `shell.defaultLocale`, one or
more content types, required `title`/`slug`/`body`, optional `summary`/`image`, and
both list/detail bindings with optional navigation. The `primary` marker is a graph
role, not an automatic homepage. Paths must use non-reserved lowercase segments
and must not overlap another collection's list/detail routes.
Other traits/bindings, multiple locales, and combining top-level composition with
application auth are explicitly rejected for now. CMS is opt-in as described below.

Generated shells include strict Astro typechecking, shared tokens and `SeoHead`.
After installing dependencies and replacing the placeholder site URL in
`astro.config.mjs`, run `pnpm typecheck` and `pnpm build`. `noIndex: true` suppresses
the sitemap and sets both robots.txt and page metadata; it is not access control.
The CLI does not configure a protected preview host.

The generated definitions record the creation input and export the collection
schemas. Changing that recorded trait list does not regenerate the rest of the
site: the CLI remains create-only.

### Add the CMS editor

Keep the same top-level `composition`. Add `cms-admin` to each editable type's
bindings and add `cms` inside `recipes`:

```json
{
  "cms": {
    "backend": {
      "repo": "YOUR_ORG/YOUR_PROJECT/YOUR_REPOSITORY",
      "tenantId": "YOUR_TENANT_ID",
      "appId": "YOUR_PUBLIC_APP_ID",
      "branch": "main"
    },
    "mediaRoots": ["src/assets/images"],
    "uiLocale": "en"
  }
}
```

This fragment belongs alongside `recipes.shell`; it is not a complete create
config. Never add a second composition inside `recipes.cms`.

Core remains the sole schema, content-route and Astro-config owner. The CMS
add-on builds Decap forms from the same composition and renders the shared
standalone AdminPage at `/admin/`. Only `cms-admin`-bound types appear in the
editor. A missing CMS selection or an editor with no bound types is an input error.

Uploads and the starter image use the first media root. All roots have explicit
source-image preview mappings and must be distinct and non-overlapping. The
generated markdown processor resolves Decap body-image URLs without changing the
public pages' optimized assets. The editor is always noindex and omitted from the
sitemap; the site's `noIndex` policy still applies.

Backend values are public identifiers, not secrets. Repository access, Entra
registration and login require separate setup. Generation neither provisions
cloud resources nor tests a live CMS session; saves target the configured branch
(default `main`). Preview-host authentication remains a separate deployment concern.

:::note[`@easy-web/create` is reserved]
The package name `@easy-web/create` is reserved for a future `pnpm create` entry point and ships no code, so `pnpm create @easy-web` does not generate a site today. Use `@easy-web/cli`. See the [`@easy-web/create` page](../../packages/create-easy-web/).
:::

### Review the generated result

Recipes belong to the packages that own the capabilities; the CLI composes their
declared outputs rather than copying a running site. A successful create adds one
generation commit, but its location depends on the target:

| Input target | Where the generated commit lives |
| :--- | :--- |
| A nonexistent directory or an empty directory without Git metadata | A new Git repository at that path, on `main`, with one initial commit |
| A clean Git root or worktree with an existing commit whose tree and index are empty | A new `easy-web-create-...` task branch in a separate worktree; the input repository's HEAD, index and files stay unchanged |

An initialized repository without a committed HEAD is not the second case.
Hidden or ignored files also make a target occupied; there is no overwrite mode.
Use the **returned `target`**, not an assumed copy of the input path, for every
subsequent command. Keep a returned task worktree until review is complete.

For automation, add `--json` to the create command. Success writes a
`schemaVersion: 1` result to stdout with `target`, `commit`, `branch`, `graphJson`
and `graphMermaid`; errors write diagnostics to stderr. The graph fields are
serialized strings in the result, not additional generated files.

Creation checks recipe options and validators, declared output paths, JSON and
JavaScript syntax, dependency source restrictions and an additions-only Git index.
It does **not** run the generated site's type checks, build or end-to-end tests.
Review and validate the result before merging or using it:

1. Inspect the returned commit and capability graph, then the generated source and
   package scripts. A generated auth mount is not mounted by the shell: selecting
   `auth` does not by itself render sign-in or configure the Astro React integration.
   Follow the [auth integration guidance](../../packages/auth/) when wiring it.
2. Resolve dependencies in the returned target with `pnpm install` if you did not
   select `--install`. The offline placeholder records specifiers, not resolved
   package snapshots; it is not ready for `pnpm install --frozen-lockfile`.
   Review and commit the completed lockfile separately. The generation default
   makes no network request, but obtaining the CLI (for example through `pnpm dlx`)
   and installing dependencies can require network access.
3. Run the site's build and applicable checks yourself. The current generated
   shell has a build script, but no `tsconfig.json` or `@astrojs/check`; add the
   required type-check setup rather than treating creation success as a passing
   Astro check. Inspect the built pages and optional integrations before accepting
   the result.

:::caution[Installation happens after the generation commit]
`--install` runs `pnpm install` in the returned target through the ambient registry
configuration. It can update the lockfile after the commit. If installation fails,
the command exits with code `4`, but the generated repository or task worktree and
commit remain; no success result is printed. Inspect that state before retrying
installation. Do not rerun create into the now-occupied target or assume that a
nonzero exit means generation was rolled back.
:::

### After creation

The site owns its generated files. Updating a recipe changes future generations;
it does not synchronize those files in existing sites. Maintain shared package
dependencies and their lockfile through reviewed updates and site-local checks,
not by rerunning create. See the [responsibility model](../../architecture/#shared-packages-and-site-responsibilities).

Hosting, executable deployment definitions, credentials and permissions are a
separate setup and review step. Creation neither provisions them nor establishes
a deployed site or PR preview environment.

## Manual Setup

Bootstrap a new site instance manually. Start from the recommended baseline: Node.js 24, pnpm 10 and Astro 7 (see [Installation](../installation/)).

### 1. Create an Astro project

```bash
pnpm create astro@latest my-site
cd my-site
```

### 2. Install easy-web

```bash
pnpm add @easy-web/core
```

`@easy-web/core` is the base package. Add-ons such as `@easy-web/cms-adapters` or `@easy-web/swa` are optional.

### 3. Add the theme to your base layout

```astro
---
// src/layouts/Base.astro
import '@easy-web/core/styles/tokens.css';
import { noFlashScript } from '@easy-web/core/theme';
import PageShell from '@easy-web/core/components/PageShell';
import Header from '@easy-web/core/components/Header';
import Footer from '@easy-web/core/components/Footer';
import ThemeToggle from '@easy-web/core/components/ThemeToggle';

const lang = 'en';
const { pathname } = Astro.url;
---
<html lang={lang}>
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width" />
    <script is:inline set:html={noFlashScript} />
  </head>
  <body>
    <PageShell lang={lang}>
      <Header
        slot="header"
        lang={lang}
        siteName="My Site"
        navItems={[{ label: 'Home', href: '/' }]}
        currentLang={lang}
        pathname={pathname}
      >
        <ThemeToggle slot="actions" lang={lang} />
      </Header>
      <slot />
      <Footer
        slot="footer"
        lang={lang}
        siteName="My Site"
        legalLinks={[{ label: 'Privacy', href: '/privacy/' }]}
      />
    </PageShell>
  </body>
</html>
```

The `actions` slot replaces the header's default controls (theme toggle plus language switch). Leave it out to keep the defaults.

### 4. Configure i18n (optional)

```typescript
// astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  i18n: {
    defaultLocale: 'en',
    locales: ['en', 'de'],
  },
});
```

### 5. Add i18n helpers

```typescript
// Use localizedHref for locale-aware links
import { localizedHref } from '@easy-web/core/i18n';

const link = localizedHref('/about', 'de'); // → '/de/about'
const defaultLink = localizedHref('/about', 'en'); // → '/about'
```

## Project Structure

```
my-site/
├── src/
│   ├── components/        # Site-specific components
│   ├── layouts/
│   │   └── Base.astro     # Uses @easy-web/core
│   ├── pages/
│   │   ├── index.astro
│   │   └── [lang]/        # i18n routes
│   └── content/           # Astro content collections
├── public/
├── astro.config.mjs
└── package.json
```
